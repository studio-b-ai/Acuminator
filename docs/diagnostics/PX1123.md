# PX1123
This document describes the PX1123 diagnostic.

## Summary

| Code   | Short Description                                                                                                                                                                                         | Type    | Code Fix    |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- | ----------- |
| PX1123 | A `PXDatabase.Execute` call performs an `INSERT INTO RolesInMember` or `INSERT INTO RolesInCache` with an explicit column list that omits `Cachetype`. The INSERT will crash at runtime. | Warning | Unavailable |

## Diagnostic Description

The Acumatica access-rights system stores role grants across three tables: `RolesInGraph`, `RolesInMember`, and `RolesInCache`.  `RolesInMember` and `RolesInCache` both have a `Cachetype` column that is declared `NOT NULL` and has no schema-level default.  `RolesInGraph` does not have this column.

When a `CustomizationPlugin` (or any other C# code that calls `PXDatabase.Execute`) performs an `INSERT INTO RolesInMember` or `INSERT INTO RolesInCache` with an **explicit column list** that omits `Cachetype`, SQL Server raises:

```
Cannot insert the value NULL into column 'Cachetype', table '...'; column does not allow nulls.
```

The INSERT fails, the role grant is not applied, and the affected screen remains inaccessible to the role — returning HTTP 404 from the Acumatica OData endpoint and not appearing in the `SM205010` access-rights tree.

This failure is particularly dangerous inside `CustomizationPlugin.UpdateDatabase` because:
- It occurs at publish-time, not at startup, so it can silently break a deploy without appearing in the build log.
- The partial-grant state (some `RolesIn*` tables updated, others not) can be hard to diagnose.

Real-world impact: the 2026-05-10 W4 outage at Heritage Fabrics — 17 Bolt GIs returned HTTP 404.  The recovery plugin's `INSERT INTO RolesInMember` crashed with the NULL `Cachetype` error, leaving role grants in a partial state that required a follow-up plugin pass to correct (Studio B CLAUDE.md Rule #45 / Rule #122).

PX1123 fires when:
1. A `PXDatabase.Execute` call is found.
2. The SQL argument contains one or more `INSERT INTO RolesInMember (...)` or `INSERT INTO RolesInCache (...)` statements with an explicit column list.
3. That column list does **not** contain `Cachetype` (case-insensitive; bracket- and double-quote-enclosed variants accepted).

PX1123 does **not** fire for:
- `INSERT INTO RolesInGraph` — that table has no `Cachetype` column.
- `INSERT INTO RolesInMember SELECT ...` (no explicit column list) — the implicit column ordering respects the table schema; the server enforces the NOT NULL constraint at that layer.

## Example of Incorrect Code

### Missing `Cachetype` in explicit column list (canonical anti-pattern)

```csharp
using PX.Data;
using Customization;

public class MyPlugin : CustomizationPlugin
{
    public override void UpdateDatabase()
    {
        // Error PX1123: Cachetype is NOT NULL on RolesInMember; this INSERT will crash.
        PXDatabase.Execute(@"
            INSERT INTO RolesInMember (ScreenID, Rolename, AccessRights, ApplicationName)
            VALUES ('SB401140', '*', 4, '/')
        ");
    }
}
```

### Multiple tables, only one with the omission

```csharp
PXDatabase.Execute(@"
    INSERT INTO RolesInGraph  (ScreenID, Rolename, AccessRights, ApplicationName)
        VALUES ('SB401140', '*', 4, '/');
    INSERT INTO RolesInMember (ScreenID, Rolename, AccessRights, ApplicationName)
        VALUES ('SB401140', '*', 4, '/');
    INSERT INTO RolesInCache  (ScreenID, Rolename, AccessRights, ApplicationName)
        VALUES ('SB401140', '*', 4, '/');
");
// Error PX1123: RolesInGraph is fine (no Cachetype), but RolesInMember and
// RolesInCache both omit it.  Both INSERTs are reported.
```

## Example of Correct Code

### Fix 1 — add `Cachetype` to the explicit column list

The `Cachetype` value for a wildcard role-grant row is typically `0` (or the value found in working rows in the same tenant — query an existing row from `RolesInMember WHERE ScreenID = '<working-screen>'` to confirm).

```csharp
PXDatabase.Execute(@"
    INSERT INTO RolesInGraph  (ScreenID, Rolename, AccessRights, ApplicationName)
        VALUES ('SB401140', '*', 4, '/');
    INSERT INTO RolesInMember (ScreenID, Rolename, AccessRights, ApplicationName, Cachetype)
        VALUES ('SB401140', '*', 4, '/', 0);
    INSERT INTO RolesInCache  (ScreenID, Rolename, AccessRights, ApplicationName, Cachetype)
        VALUES ('SB401140', '*', 4, '/', 0);
");
```

### Fix 2 — use `INFORMATION_SCHEMA.COLUMNS` for dynamic discovery

This pattern is safer across Acumatica versions because it automatically includes any columns added by the platform in future releases:

```csharp
// Build the INSERT dynamically at runtime so unknown columns default to their
// schema-defined defaults rather than requiring a hardcoded column list.
PXDatabase.Execute(@"
    DECLARE @sql NVARCHAR(MAX);
    SELECT @sql = 'INSERT INTO RolesInMember ('
        + STRING_AGG(COLUMN_NAME, ', ')
        + ') SELECT '
        + STRING_AGG(
            CASE COLUMN_NAME
                WHEN 'ScreenID'       THEN '''SB401140'''
                WHEN 'Rolename'       THEN '''*'''
                WHEN 'AccessRights'   THEN '4'
                WHEN 'ApplicationName' THEN '''/'''
                WHEN 'Cachetype'      THEN '0'
                ELSE 'NULL'
            END, ', ')
        + ' WHERE NOT EXISTS (
              SELECT 1 FROM RolesInMember
              WHERE ScreenID = ''SB401140'' AND Rolename = ''*'')'
    FROM INFORMATION_SCHEMA.COLUMNS
    WHERE TABLE_NAME = 'RolesInMember';
    EXEC sp_executesql @sql;
");
```

The reference implementation pattern used in the `EnsureScreenRights` plugin in the Heritage Fabrics `AesthetikContainersInstall.cs` follows this dynamic-discovery approach.

## Suppression

If the call is intentionally omitting `Cachetype` (for example, when targeting a custom or non-standard Acumatica build where the column does not exist), suppress with a comment:

```csharp
// Acuminator disable once PX1123 — target environment does not have Cachetype column; confirmed with DBA.
PXDatabase.Execute(@"
    INSERT INTO RolesInMember (ScreenID, Rolename, AccessRights, ApplicationName)
        VALUES ('SB401140', '*', 4, '/')
");
```

Or use a suppression file when Acuminator is installed as a VSIX extension.

## Heuristic Limitations

The diagnostic is regex-based and does not perform a full T-SQL parse.  The following patterns are known limitations:

- **Dynamic SQL built at runtime** (for example, `StringBuilder`-composed SQL with non-constant fragments) cannot be analyzed statically; PX1123 silently skips these calls.
- **Column list spread across multiple string concatenation pieces** where the parentheses are not in the same constant fragment — these calls are skipped because the regex requires both the `(` and `)` of the column list to appear in a single analyzable string.
- **Interpolation holes that stand in for column names** (for example, `$"INSERT INTO RolesInMember ({columnList}) VALUES ..."`) are not modeled; the hole is replaced with a whitespace placeholder that will not match `Cachetype`.
- **INSERT without any column list** (for example, `INSERT INTO RolesInMember SELECT ... FROM RolesInGraph`) is intentionally not flagged because the schema enforces the NOT NULL constraint at the server level and the pattern is correct.
